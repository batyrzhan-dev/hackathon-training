# CASE — AI-помощник городского оператора

Статус: review одобрен с уточнениями; решения ниже зафиксированы по итогам review. Этапы CASE → VALUE → WOW → MVP → ARCH → SCORE подготовлены; BUILD и DEMO не начаты. Все функции ниже — проектируемые, не реализованные.

## 1. Original task

AI-система для обработки обращений жителей города

Городские службы ежедневно получают большое количество текстовых обращений жителей: проблемы с дорогами, освещением, мусором, водоснабжением, дворами и другими объектами инфраструктуры.

Операторам приходится вручную читать обращения, определять категорию, находить похожие обращения и определять их приоритетность.

Необходимо разработать AI-решение, которое помогает сотруднику городской службы обрабатывать поступающие обращения.

Решение должно:

- принимать текст обращения;
- автоматически определять категорию проблемы;
- выявлять похожие/дублирующиеся обращения;
- формировать краткое описание проблемы;
- помогать определить приоритет обработки;
- показывать результат сотруднику в понятном интерфейсе.

Необходимо продемонстрировать работающий прототип и объяснить потенциал дальнейшего развития решения.

## 2. Problem — CASE

Оператор вручную преобразует свободный текст в рабочую карточку и ищет уже зарегистрированные сообщения о той же проблеме. Нужно уменьшить объём повторного чтения и сделать основания приоритета видимыми.

Обязательные требования: все шесть функций из исходного задания, работающий прототип и объяснение развития. Нельзя потерять формулировки «похожие/дублирующиеся» и «помогать определить»: система предлагает, сотрудник проверяет.

Кейс не задаёт стек, модель, бюджет, сроки, языки, датасет, регламент приоритизации и численные критерии качества. Принятые ниже решения — допущения для тренировки, а не требования организаторов. Критерии SCORE взяты из playbook; официальные веса неизвестны.

Границы первого прототипа: русский текст, один оператор, небольшая синтетическая история обращений, без интеграции с городскими системами. Система не проверяет истинность жалобы и не отправляет службы автоматически.

## 3. Target user

Основной пользователь — сотрудник городской службы, выполняющий первичную обработку обращений. Житель является автором входного текста; отдельный кабинет жителя в MVP не нужен.

## 4. Value proposition — VALUE

Оператор городской службы сталкивается с потоком разрозненных жалоб. Наше решение использует AI, чтобы превратить текст в краткую карточку и найти связанные обращения; оператор получает категорию, контекст повторов и объяснимую рекомендацию приоритета в одном экране.

Ожидаемая польза — меньше ручного чтения и поиска. Эффект пока не измерен; для проверки сравнить время ручной обработки и обработки с помощником на одинаковом наборе обращений, чередуя порядок заданий.

### Выбор концепции по итогам review

| Концепция | Основной сценарий и AI | Обычная логика / MVP / WOW | Риск и соответствие кейсу |
|---|---|---|---|
| Карточка оператора — одобрена | Текст → извлечение категории и краткого описания → семантический поиск | Валидация, правила приоритета; MVP — одна карточка с историей; WOW — сравнение возможного дубля с источником | Нужна проверка ложных дублей; напрямую покрывает все шесть требований |
| Очередь с группировкой обращений | Пакет текстов → AI-группировка проблем | Подсчёт и сортировка групп; MVP — очередь и карточки; WOW — сводка повторов | Больше данных и интерфейса, сложнее показать индивидуальную обработку за минуту |
| Карта городских проблем | Текст → извлечение проблемы и адреса | Геокодирование и отображение; MVP — карта с карточкой; WOW — территориальные скопления | Адреса могут отсутствовать, нужна внешняя интеграция; карта не обязательна в кейсе |

Для первого вертикального сценария одобрена карточка оператора.

Human-in-the-loop — важная особенность решения: AI помогает анализировать поток обращений, проверяемые решения остаются объяснимыми, а потенциально ошибочные связи дублей подтверждаются или отклоняются человеком. Автоматического объединения исходных записей нет.

## 5. Main demo scenario — WOW, 30–60 секунд

Синтетический вход: «На улице Учебной, 12, у подъезда второй день не горит фонарь. Сегодня из столба торчит провод и искрит, рядом ходят дети».

1. 0–10 с: оператор вставляет текст и запускает анализ.
2. 10–25 с: система получает текст и историю; AI предлагает категорию «Освещение», краткое описание, адрес и признак опасности с цитатой «торчит провод и искрит».
3. 25–35 с: семантический поиск находит старое сообщение «У подъезда дома 12 на Учебной темно, фонарь не работает». Код показывает его как возможный дубль при совпадении места и условий события; сообщение о фонаре у другого дома остаётся просто похожим.
4. 35–45 с: код показывает score = 50, priority = MEDIUM и reasons: safety risk +40, multiple days +10. При одном probable duplicate надбавки за повторы нет; неисправность одного фонаря сама по себе не считается critical service outage. Если история содержит три подходящих probable duplicate reports, score = 70 и priority = HIGH.
5. 45–60 с: оператор открывает сравнение, видит новое обстоятельство об искрении, подтверждает или отклоняет каждый probable duplicate; код пересчитывает score при отклонении кандидата. Исходные обращения сохраняются отдельно.

Жюри видит: система связывает разные формулировки, сохраняет новое важное обстоятельство и объясняет рекомендацию. Времена — целевой сценарий, не измеренная производительность.

## 6. MVP MUST

Основной сценарий: обращения → AI analysis → structured data → probable duplicate detection → deterministic priority → operator card → human confirmation of duplicates.

- Поле текста, кнопка анализа, состояния ожидания, успеха и ошибки.
- Реальная AI-классификация: дороги / освещение / мусор / водоснабжение / дворы / другое; один основной класс, при неоднозначности — флаг проверки.
- Краткое описание в 1–2 предложениях, без добавления фактов.
- Поиск probable duplicates по category, normalized location/object и semantic/text similarity. Каждый кандидат имеет численный similarity и статус pending/confirmed/rejected. Карточка первоначально показывает top-3 с возможностью открыть остальных; подсчёт для scoring выполняется по всему набору кандидатов, а не только видимым трём.
- Детерминированный результат: score, priority HIGH/MEDIUM/LOW и reasons с отдельным вкладом каждого сработавшего правила; неполный анализ явно отмечается.
- Один экран с исходником, результатом, основаниями, похожими обращениями и возможностью проверить/исправить категорию и извлечённые признаки с пересчётом score, подтвердить/отклонить связь.
- Сохранение текста, предложений AI, рассчитанного результата и решения оператора раздельно.
- Синтетическая история, позитивные и негативные примеры, обработка ошибок AI. Никаких заранее зашитых результатов вместо анализа.

Порядок: MUST целиком → WOW → SHOULD. Публичный доступ и воспроизводимый запуск нужны к будущему завершению прототипа по playbook, но не выполняются в текущем этапе.

## 7. WOW feature и остальной scope

WOW: сравнение нового текста и возможного дубля рядом, с подсветкой точных цитат, объясняющих опасность и совпадение места. Подсветка дополняет обязательные основания в карточке; не требует второго генеративного ответа.

SHOULD: фильтр истории по категории/приоритету, быстрый выбор демо-примеров, отображение времени анализа.

Не входят в MVP: authentication, roles, map, production integrations, complex admin panel, enterprise infrastructure.

LATER: перечисленные исключения, городская CRM, автоназначение служб, геокодирование, массовая загрузка, мультиязычность и сложная аналитика.

## 8. AI role

AI отвечает за понимание свободного текста, категорию, краткое описание, извлечение явно упомянутого места, времени события и признаков опасности/нарушения услуги с точными цитатами. Семантические embeddings нужны для поиска разных формулировок одной проблемы.

Почему нужен AI: «во дворе темно» и «не работает фонарь» семантически связаны, но не обязаны иметь общие ключевые слова. Неструктурированные жалобы содержат неоднозначность, отрицания и несколько обстоятельств.

AI НЕ определяет итоговый HIGH/MEDIUM/LOW и score, не назначает итоговый приоритет, не рассчитывает пороги и сортировку, не объединяет записи, не назначает службы, не придумывает адрес и время. Текст обращения — данные, а не инструкции модели. Признаки AI остаются гипотезами: наличие цитаты подтверждает источник, но не гарантирует правильную интерпретацию.

## 9. Deterministic logic

Код валидирует вход и ответ AI, проверяет допустимые категории, наличие цитат в исходном тексте, вычисляет cosine similarity, фильтрует и сортирует кандидатов, применяет таблицу приоритетов и сохраняет решения оператора.

### Priority: deterministic scoring model — demo rules

Это демонстрационные правила (demo rules), а не реальные нормативы городской службы. AI извлекает признаки с цитатами; код независимо рассчитывает сумму и итоговый HIGH/MEDIUM/LOW.

| Признак | Вклад в score | Основание |
|---|---:|---|
| safety risk | +40 | Явный риск безопасности и цитата |
| critical infrastructure/service outage | +30 | Явное нарушение критической инфраструктуры/услуги и цитата |
| 3 or more probable duplicate reports | +20 | Не менее трёх других уникальных обращений-кандидатов, их ID и similarity |
| problem persists for multiple days | +10 | Явно указано минимум два дня, цитата или извлечённая длительность |

Каждое условие добавляет баллы один раз; score = сумма вкладов, диапазон 0–100. Один текст может давать несколько разных вкладов. LOW: 0–29; MEDIUM: 30–59; HIGH: 60+. Итог не выдаётся моделью и не переопределяется произвольно: исправление оператором входных признаков приводит к повторному расчёту.

Для demo critical outage означает явно описанное отсутствие критической услуги (например, воды во всём доме) или нарушение критического объекта; не любая поломка получает +30. Multiple days — минимум два дня по тексту, не возраст записи в БД. Safety risk сам по себе даёт 40/MEDIUM по одобренной модели; это не оценка реальной безопасности и не SLA.

Для +20 считать другие уникальные ID probable duplicates текущего обращения, без самого обращения и без отклонённых оператором связей. Pending и confirmed учитываются; подтверждение сохраняет вклад, отклонение пересчитывает число и score. До проверки показать, что вклад основан на probable duplicates; связь и исходные тексты сохраняются отдельно. Три сообщения всего, включая текущее, означают только два других кандидата и не дают +20.

Результат показывает score, priority и reasons: rule_id, points, цитату или список ID, участвовавших в начислении. При нуле — пустой список вкладов и пояснение «условия начисления не выявлены». При неизвестном признаке/сбое поиска не подменять неизвестность отсутствием: показать неполный анализ, доступный subtotal и причины неопределённости; итоговые score/priority остаются не рассчитаны до успешного анализа или проверки признаков оператором.

### Probable duplicate detection и human confirmation

Поиск — по всему набору истории с cosine similarity выше T_similar; top-3 ограничивает только первоначальное отображение. Метка «возможный дубль» требует более строгого T_duplicate, совпадения category и normalized location/object (нормализованного явно указанного места/объекта), открытого статуса старого обращения и отсутствия явного противоречия времени события. Неизвестное место/время ограничивает результат меткой «похожее; нужна проверка». Для главного демо оба текста явно описывают продолжающуюся неисправность одного фонаря.

Каждый probable duplicate показывает численный similarity (cosine similarity, диапазон −1…1), совпавшие категорию/место/объект и статус pending/confirmed/rejected. Это мера близости, не калиброванная вероятность: отдельный confidence без калибровки не заявляется. Окончательное подтверждение или отклонение делает оператор; подтверждение создаёт связь, а не сливает записи.

Нормализация места/объекта в MVP — регистр, пробелы и небольшой задокументированный словарь сокращений; геокодирования нет. Совпадение адреса не доказывает совпадение объекта: окончательную связь подтверждает оператор. История хранит статус и дату создания; дата регистрации не подменяет дату события.

Численные пороги не назначены произвольно: их предстоит выбрать на отдельном калибровочном наборе пар для выбранной модели, зафиксировать вместе с версией модели и проверить на отложенных примерах. Равные similarity сортируются по ID. Текущее обращение исключается из собственной выдачи. При отсутствии подходящих кандидатов показывается пустой результат; при сбое поиска — ошибка поиска, а не «дублей нет».

## 10. Input

Непустой русский текст, проектный лимит 5 000 символов после trim. Адрес необязателен. Дополнительный контекст — сохранённая история синтетических обращений с ID, датой и статусом. Никаких обязательных вложений и внешних API городской инфраструктуры.

## 11. Output

Карточка: исходный текст, категория, summary, извлечённое место или «не указано», score, priority HIGH/MEDIUM/LOW, reasons с баллами и источниками, предупреждения, кандидаты с ID/текстом/типом связи/similarity/статусом подтверждения, решение оператора. Similarity — техническая мера близости, не вероятность дубля.

Проектный контракт AI: category, summary, location|null, event_time_text|null, ongoing|unknown, safety_risk, critical_outage и persists_multiple_days со значениями yes/no/unknown и evidence, review_reasons. Evidence содержит точные цитаты, для которых код проверяет вхождение в исходник. Контракт backend дополняет результат полями score, priority, reasons[{rule_id, points, evidence_or_ids}], probable_duplicate_count, candidates[{id, similarity, status}] и analysis_status; ID, время и статус задаёт приложение.

## 12. Architecture — ARCH

```text
Оператор → UI: текст → Backend: валидация
                         ↓
                AI: извлечение + summary
                         ↓
                 Проверка структуры/цитат
                         ↓
                Embedding нового обращения
                         ↓
История + сохранённые embeddings → similarity и кандидаты
                         ↓
         Probable duplicate detection + подсчёт кандидатов
                         ↓
         Deterministic priority: score → HIGH/MEDIUM/LOW
                         ↓
        Operator card: score + priority + reasons
                         ↓
        Human confirmation/rejection of duplicates
                         ↓
        Пересчёт при изменении кандидатов → сохранение связей
```

Один backend обслуживает UI, AI-вызовы, историю и правила. База хранит обращения, извлечённые признаки, embeddings с версией модели и операторские решения. Поиск выполняется по небольшому набору в памяти; отдельная векторная БД не нужна. История заранее проходит тот же AI-процесс; её подготовка не входит в минутное live demo.

AI API-ключ хранится только на backend. После подтверждения запись попадает в историю; повторная отправка подтверждения с тем же ID не создаёт новую запись. Не сохранять полные тексты в технических логах. Для демо использовать только синтетические данные.

Объяснение приоритета строится шаблоном из reasons, баллов, цитат и ID кандидатов; повторный вызов AI для объяснения не нужен. При отказе AI интерфейс сохраняет введённый текст, показывает ошибку и позволяет повторить; ручное решение явно отмечается как ручное.

## 13. Stack

Предложение для review, зависимости не установлены и совместимость не проверена:

- Backend: Python + FastAPI; валидация структурированного ответа — Pydantic.
- Frontend: серверные HTML-шаблоны Jinja2 и небольшой JavaScript для одной карточки.
- AI: внешний API текстовой модели со структурированным ответом и embedding-модели; провайдер и точные model ID выбираются после review с учётом доступов, бюджета и качества русского языка.
- Storage: SQLite, embeddings в сохранённых записях; cosine similarity в приложении.
- Deployment: один сервис с persistent disk для SQLite; конкретная площадка пока не выбрана. Проверить ранний deployment после первого вертикального среза.

Это одна из простых реализаций; отсутствие выбранного AI-провайдера — открытая зависимость перед BUILD.

## 14. Error cases

| Случай | Ожидаемое поведение |
|---|---|
| Пустой/слишком длинный ввод | Понятная ошибка до AI-вызова |
| Нет адреса | Анализ продолжается; возможный дубль не утверждается |
| Несколько проблем/противоречия | Основная категория с флагом проверки; существенные обстоятельства сохраняются в summary |
| Отрицание «провод не искрит» | Не извлекать положительный safety_risk; включить в проверочный набор |
| Инструкции внутри жалобы | Не менять правила/схему ответа; проверять выход |
| Таймаут, rate limit, невалидный JSON | Явная ошибка/неполный анализ; повтор по действию пользователя |
| Поиск недоступен | Статус «поиск не выполнен»; не заявлять отсутствие дублей |
| Нет похожих записей/история пуста | Честное отсутствие кандидатов |
| Ошибка записи в БД | Не показывать «сохранено»; введённые данные остаются на экране |
| Исправление категории оператором | Перепроверить метку возможного дубля; сохранить исходное предложение и исправление |

| H04 | На Примерной, 7, сегодня весь дом без воды. | critical_outage +30 → MEDIUM при отсутствии других вкладов |
| H05 | Во дворе у дома 3 на Тестовой небольшая яма. Проезд свободен. | score 0 → LOW при отсутствии других вкладов |
| H06 | Вчера у дома 12 на Учебной фонарь починили, сейчас всё работает. | Закрытая запись, не текущий дубль |
| H07 | Во дворе темно, фонарь не работает. | Адрес неизвестен; только похожее |
| H08 | На Учебной, 12, провод не искрит, оголённых проводов нет; лампа не горит. | Проверка отрицаний |

Перед BUILD-разметкой дополнить набор до 24 обращений (по 4 на категорию) и 24 пар: 8 дублей, 8 похожих, но разных событий, 8 нерелевантных. Разделить пары поровну на калибровочные и отложенные, по 4 каждого типа в части; не допускать общих обращений между частями. Отложенные примеры не использовать для подбора порогов. Это небольшой smoke-набор, не доказательство промышленного качества.

## 16. Success criteria

Проектные критерии приёмки будущего прототипа; сейчас не проверены:

1. Оператор вводит произвольное новое обращение и получает все шесть результатов из кейса в одном потоке.
2. Главное демо проходит за 30–60 секунд; цель для самого анализа — до 15 секунд на подготовленной истории, проверить тремя последовательными прогонами и записать реальные времена.
3. На 24 размеченных обращениях верная основная категория минимум у 20; сводки не добавляют фактов во всех проверенных примерах. Ошибки публикуются вместе с результатом.
4. На 12 отложенных парах: ни один размеченный не-дубль не помечен возможным дублем; не менее 3 из 4 дублей найдены в top-3. Состав истории при проверке фиксирован.
5. Scoring воспроизводим: проверить все 16 сочетаний четырёх признаков, сумму и reasons; границы преобразования score 0/29/30/59/60/100. Отдельно проверить два/три probable duplicates, исключение самого обращения, отсутствие повторного подсчёта ID, пересчёт после rejection и отсутствие двойного начисления. Safety risk без других признаков даёт 40/MEDIUM, с multiple days — 50/MEDIUM, с тремя кандидатами и multiple days — 70/HIGH. Сырые тексты с отрицанием и неизвестностью проверяют AI-извлечение отдельно; неполный анализ не получает ложный итоговый LOW.
6. Каждый probable duplicate содержит similarity; можно открыть источник, подтвердить/отклонить связь и перечитать сохранённое решение оператора. Pending → confirmed/rejected фиксируется явно. Нет автоматического объединения или потери исходников; score/priority/reasons остаются согласованными после пересчёта.
7. Ошибки из раздела 14 показаны корректно; реальный AI подтверждён вызовами и результатами, без раскрытия секретов.
8. К завершению будущего BUILD: воспроизводимый запуск по README и проверенный публичный URL.
