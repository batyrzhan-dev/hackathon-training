# PLAN — CASE → VALUE → WOW → MVP → ARCH → SCORE

Статус: review завершён; BUILD разрешён только для Phase 1 по новому запросу пользователя. Реальный AI, duplicate detection, SQLite и deployment отложены. Commit и push не разрешены.

## 1. CASE

Источник требований дословно сохранён в CASE.md, раздел 1. Пользователь — оператор городской службы, вход — текст жителя, выход — карточка обработки. Все продуктовые допущения отделены от опубликованного задания.

| Требование кейса | Проектируемый результат | Будущее доказательство |
|---|---|---|
| Принимать текст | Поле ввода и валидация | Новый текст проходит весь сценарий; пустой отклоняется |
| Определять категорию | Один основной класс + возможность исправления | Размеченный набор и отчёт по ошибкам |
| Похожие/дубли | Category + normalized location/object + semantic/text similarity; probable duplicates с similarity и решением оператора | Дубль-перефразировка найден; другой адрес не объявлен дублем |
| Краткое описание | 1–2 предложения без новых фактов | Сопоставление сводки и источника |
| Помогать с приоритетом | Детерминированные score, HIGH/MEDIUM/LOW и reasons с вкладом каждого правила | Табличные тесты правил + сквозные AI-примеры |
| Понятный интерфейс | Одна карточка, источники, подтверждение/исправление | Оператор проходит поток без устных подсказок |
| Прототип и развитие | Реальный end-to-end, план расширения | Live demo, запуск по README, раздел развития |

## 2. VALUE

Одобрена концепция карточки оператора. Очередь с группировкой и карта рассмотрены в CASE.md; они добавляют объём без необходимости для основного сценария. Польза — сократить ручное чтение и поиск при сохранении контроля сотрудника. Ускорение пока является гипотезой, не заявленным достижением.

## 3. WOW

Один 30–60-секундный сценарий: жалоба о фонаре с новым признаком опасности → категория и summary → probable duplicate с similarity → score 50/MEDIUM (+40 risk, +10 multiple days) → подтверждение/отклонение связи оператором. WOW-дополнение: тексты рядом и подсветка источников. При трёх других probable duplicate reports добавляется +20: в этом примере 70/HIGH; один повтор надбавки не даёт.

## 4. MVP

Основной сценарий: обращения → AI analysis → structured data → probable duplicate detection → deterministic priority → operator card → human confirmation of duplicates.

Не входят в MVP: authentication, roles, map, production integrations, complex admin panel, enterprise infrastructure.

| Приоритет | Граница |
|---|---|
| MUST | Ввод, реальный AI, summary, категория, probable duplicate detection с similarity, deterministic scoring, карточка score/priority/reasons, human confirmation/rejection, сохранение, обработка ошибок |
| WOW | Сравнение источников и подсветка цитат |
| SHOULD | Фильтры истории, выбор примеров, отображение длительности |
| LATER | Authentication, roles, map, production integrations, complex admin panel, enterprise infrastructure; массовый импорт и мультиязычность |

Если времени мало, сокращать SHOULD и WOW. Не вырезать ни одну из шести обязательных функций. Если AI-провайдер недоступен, обозначить блокер; записанный результат можно показывать только как явно подписанный пример, он не заменяет работающий прототип.

## 5. ARCH

Один Python/FastAPI-сервис, простой HTML-интерфейс, SQLite, внешний текстовый AI и embeddings. Точные модели и хостинг остаются открытыми. Поток и контракты — CASE.md, разделы 8–13.

AI: категория, summary, признаки с цитатами, семантическое представление. Код: валидация, cosine similarity, пороги, правила приоритета, сортировка, хранение. Оператор: проверка/исправление категории и признаков, подтверждение или отклонение дублей; исправления вызывают пересчёт. AI не определяет итоговый HIGH/MEDIUM/LOW. Анализ и операторские решения хранятся раздельно.

### Priority — согласованная demo scoring model

| Условие | Баллы |
|---|---:|
| safety risk | +40 |
| critical infrastructure/service outage | +30 |
| 3 or more probable duplicate reports | +20 |
| problem persists for multiple days | +10 |

Каждый вклад начисляется один раз. 0–29 LOW; 30–59 MEDIUM; 60+ HIGH. Это demo rules, не реальные нормативы городской службы. Карточка показывает score, priority и reasons с баллами и основаниями. AI извлекает признаки; код считает сумму и определяет класс.

Считать другие уникальные ID кандидатов по всему набору, а не только top-3 на экране; текущее обращение и rejected исключаются. Pending и confirmed учитываются. Отклонение дубля запускает пересчёт, подтверждение сохраняет вклад. Multiple days — минимум два дня по содержанию, а не возраст записи. Детальные условия и обработка неизвестности — CASE §9: неполный анализ показывает subtotal и неизвестные признаки без ложного итогового LOW.

### Probable duplicates и human-in-the-loop

Признаки: category, normalized location/object, semantic/text similarity. Каждый probable duplicate показывает численный similarity и pending/confirmed/rejected; similarity не выдаётся за вероятность. Окончательное подтверждение или отклонение — за оператором. Подтверждение сохраняет связь, исходные записи автоматически не объединяются.

Human-in-the-loop — важная особенность: AI помогает анализировать поток обращений, решения остаются объяснимыми и проверяемыми, а потенциально ошибочные объединения требуют человека. В MVP объединение записей вообще не выполняется.

Будущие проверки: все 16 сочетаний scoring-признаков и границы 29/30/59/60, правильные reasons, два/три кандидата, уникальные ID, подтверждение/отклонение с пересчётом, неизвестные признаки и отрицания. Для демо safety risk + multiple days = 50/MEDIUM; добавление трёх probable duplicates даёт 70/HIGH.

Риски и меры:

| Риск | Мера и будущая проверка |
|---|---|
| Ложный дубль | Различать похожесть и дубль, проверять место/событие, similarity и human confirmation/rejection; отрицательные пары и пересчёт score |
| Пропуск опасности / неверное отрицание | Цитаты, статус неопределённости, оператор; сквозные примеры с опасностью и отрицаниями |
| Придуманные факты | Проверка цитат и ручная оценка summary на контрольном наборе |
| Задержка/отказ AI | Ограничение длины ввода, таймаут и явная ошибка; замер трёх прогонов |
| Неизвестны доступы и бюджет | До BUILD выбрать доступного провайдера и лимиты; не предполагать наличие ключей |
| Потеря истории на хостинге | Persistent disk и проверка перезапуска после раннего deployment |
| Недостоверные метрики | Отдельные калибровочные/отложенные данные, фиксировать модель, пороги и ошибки |

## 7. Решения review и точка остановки

Review одобрен. Зафиксированы основной поток MVP, шесть исключений из scope, демонстрационный scoring, probable duplicate detection с similarity и human-in-the-loop. Необходимые уточнения до реализации: доступный AI API/бюджет, длительность тренировки, площадка deployment; при наличии — официальный регламент приоритетов и отдельные критерии организаторов. Demo scoring не подменяет городской регламент.

Обновлённая точка остановки: после реализации и проверки Phase 1. Новый запрос явно разрешает application code только для минимального vertical slice, сохраняя запрет на commit и push.

При отдельном запросе на реализацию будущий порядок: один вертикальный сценарий со всеми MUST → ранний deployment → проверка качества и ошибок → WOW → README с проверенными командами → репетиция. Каждый час оставлять проверяемые изменения или результаты проверки; commit/push возможны только по отдельному явному запросу.

## 8. BUILD — Phase 1

Реализовано в Phase 1: FastAPI + Pydantic, Jinja2/HTML, поле и Analyze, mock со structured AIAnalysis, независимый scoring engine, score/priority/reasons, синтетические примеры, валидация и unit/integration tests.

Не реализуется: real AI provider, embeddings, duplicate detection, SQLite, authentication, deployment, сложный frontend, полный dataset. Требования основного MVP выше не являются заявлением об их реализации на этом этапе.

Engine поддерживает все четыре правила. В Phase 1 duplicate count для расчёта равен 0 по явной договорённости этапа; фактическое число не измерено. Отсутствие поиска обозначается в UI/API. При unknown признаке нет ложного итогового LOW; показываются subtotal и причина проверки.

Проверка готовности: запустить pytest, затем Uvicorn; проверить живые HTML/API запросы — фонарь 50/MEDIUM, HIGH 80, LOW 0, пустой ввод 422. README должен содержать воспроизводимые команды. После проверки остановиться без перехода к следующим фазам.

Результат проверки Phase 1: 61 тест прошёл; pip check — без конфликтов. Uvicorn запущен локально, HTML/API подтверждают 50/MEDIUM, 40/MEDIUM, 80/HIGH, 0/LOW, unknown без итогового приоритета и пустой ввод 422. Chrome: demo → Analyze → карточка, structured analysis, мобильная ширина и пустой ввод проверены. Два deprecation warnings относятся к зависимостям тестового клиента. Phase 1 завершена; дальнейшие фазы не начинались. Commit/push не выполнялись.
