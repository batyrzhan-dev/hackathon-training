HACKATHON PLAYBOOK
Формула: CASE → VALUE → WOW → MVP → ARCH → SCORE → BUILD → DEMO

Цель:
Сначала понять задачу и выбрать сильный сценарий, затем реализовать минимальный работающий продукт, который максимально соответствует критериям хакатона.

==================================================
0. ПРАВИЛА, КОТОРЫЕ НЕЛЬЗЯ ЗАБЫТЬ
==================================================

1) После официального старта вся конкурсная разработка ведется только в официальном репозитории команды.
2) Использование заранее созданного кода, библиотек, моделей, шаблонов, датасетов и других внешних материалов нужно раскрыть.
3) Каждый час должен быть подтверждаемый промежуточный результат:
   - commit / изменения в репозитории;
   - рабочая функция;
   - прототип;
   - архитектура;
   - дизайн;
   - настройка модели;
   - тестирование;
   - подготовленные данные;
   - другой реальный прогресс.
4) Проект должен быть развернут и доступен по рабочей ссылке.
5) README должен позволять понять проект и запустить его без устного объяснения.
6) Не откладывать deployment на самый конец.
7) Не строить production-систему. Главная цель — работающий end-to-end сценарий.

==================================================
1. CASE — РАЗБОР КЕЙСА
==================================================

Сначала НЕ писать код.

Получить полный текст задания и ответить:

- Какую конкретную проблему нужно решить?
- Кто целевой пользователь?
- Что пользователь дает системе на вход?
- Что система должна вернуть на выходе?
- Какие требования обязательны?
- Какие ограничения есть?
- Есть ли обязательный AI/инструмент/технология?
- Какой результат можно показать на демо?
- Какие формулировки из задания нельзя потерять?
- Что будет считаться успешным выполнением кейса?

Сделать краткое резюме:

ПРОБЛЕМА:
...

ПОЛЬЗОВАТЕЛЬ:
...

ВХОД:
...

РЕЗУЛЬТАТ:
...

ОБЯЗАТЕЛЬНО:
...

ОГРАНИЧЕНИЯ:
...

==================================================
2. VALUE — ЦЕННОСТЬ
==================================================

Сформулировать решение одной фразой:

"[Пользователь] сталкивается с [проблемой].
Наше решение использует [AI/технологию], чтобы [конкретное действие]
и получить [понятный полезный результат]."

Проверка:
- понятно ли, кому это нужно?
- понятна ли реальная проблема?
- понятен ли выигрыш пользователя?
- можно ли объяснить ценность за 20 секунд?

Если нет — идею нужно упростить.

==================================================
3. WOW — ГЛАВНЫЙ DEMO-СЦЕНАРИЙ
==================================================

Выбрать ОДИН главный сценарий.

Формат:

1. Пользователь делает ...
2. Система получает ...
3. AI выполняет ...
4. Обычный код проверяет / рассчитывает ...
5. Пользователь получает ...

Пример структуры:

загрузил документ
→ AI понял содержание
→ система нашла проблему
→ вычислила результат
→ показала понятное решение

Главный сценарий должен демонстрироваться примерно за 30–60 секунд.

Вопрос:
"Что жюри увидит такого, после чего сразу поймет ценность продукта?"

==================================================
4. MVP — ЧТО РЕАЛИЗУЕМ
==================================================

Разделить функции на 4 категории.

MUST
Без этого главный сценарий не работает.

SHOULD
Полезно, если останется время.

WOW
1–2 функции, которые делают решение заметным.

LATER
Регистрация, сложные роли, полноценная админка, масштабная инфраструктура и другие вещи, которые не нужны для демонстрации основной идеи.

Правило:
Сначала полностью работающий MUST.
Потом WOW.
Только потом остальное.

==================================================
5. ARCH — АРХИТЕКТУРА
==================================================

До реализации нарисовать поток данных.

Шаблон:

USER
  ↓
INPUT / FILE / API
  ↓
AI
  ↓
STRUCTURED DATA
  ↓
DETERMINISTIC BUSINESS LOGIC
  ↓
RESULT
  ↓
AI EXPLANATION / RECOMMENDATION
  ↓
UI

Для каждого блока определить ответственность.

AI использовать там, где нужны:
- понимание неструктурированного текста;
- извлечение данных;
- классификация;
- анализ естественного языка;
- генерация;
- поиск смысловых связей.

Обычный код использовать там, где нужны:
- формулы;
- проверки правил;
- сравнения;
- фильтрация;
- подсчет;
- бизнес-ограничения;
- валидация;
- ranking по четким правилам.

Обязательный вопрос:
"Почему здесь нужен AI?"

Если задача надежнее решается if / SQL / формулой — использовать обычный код.

==================================================
6. SCORE — ПРОВЕРКА ПО КРИТЕРИЯМ
==================================================

Не ставить себе субъективный балл.
Для каждого критерия должно быть конкретное доказательство.

ТЕХНИЧЕСКИЙ ОТБОР

ПРОБЛЕМА И ЦЕННОСТЬ
- кто пользователь?
- какая проблема?
- какая польза?
- соответствует ли решение кейсу?

ФУНКЦИОНАЛЬНОСТЬ ПРОТОТИПА
- есть ли реально работающий end-to-end сценарий?
- можно ли его запустить?
- можно ли проверить основной результат?

ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ
- backend реально работает?
- AI реально подключен?
- основные компоненты связаны?
- бизнес-логика не фейковая?
- ошибки обрабатываются?

ПРАКТИЧЕСКАЯ ПРИМЕНИМОСТЬ
- кто сможет использовать решение?
- где оно применяется?
- какую реальную задачу закрывает?

ПОТЕНЦИАЛ РАЗВИТИЯ
- что можно добавить после хакатона?
- можно ли применить в других организациях?
- можно ли расширить на другие сценарии / отрасли?

README И ВОСПРОИЗВОДИМОСТЬ
README должен содержать:
- Problem;
- Target users;
- Solution;
- Key features;
- Architecture;
- AI role;
- Tech stack;
- How to run;
- Demo data;
- Deployment URL;
- External materials;
- Future development.

DEMO DAY

ЦЕННОСТЬ
- можно ли объяснить пользу быстро и понятно?

РЕЗУЛЬТАТ И КАЧЕСТВО
- работает ли заявленный пользовательский сценарий?
- выглядит ли результат целостным?

ИННОВАЦИОННОСТЬ
- чем решение отличается от простого ChatGPT-wrapper?
- есть ли собственная механика / workflow / преимущество?

МАСШТАБИРОВАНИЕ
- как продукт можно расширять?
- для каких еще пользователей / организаций он подойдет?

ПРЕЗЕНТАЦИЯ И DEMO
- есть ли четкий рассказ?
- есть ли live demo?
- подготовлены ли ответы на вопросы?

==================================================
8. BUILD — РЕАЛИЗАЦИЯ ЧЕРЕЗ CODEX
==================================================

Только после утверждения CASE.md переходить к Codex.

Первый prompt для Codex должен содержать:

- путь официального репозитория;
- краткое описание задачи;
- MVP MUST;
- главный demo flow;
- архитектуру;
- роль AI;
- что AI НЕ должен делать;
- используемый стек;
- demo data;
- ошибки;
- тесты;
- критерий готовности.

Не просить Codex сразу построить огромную систему.

Работать вертикальными срезами:

Input
→ Backend
→ AI
→ Logic
→ Result
→ UI

Сначала один рабочий сценарий целиком.
Потом расширять.

==================================================
9. ПОЧАСОВАЯ РАБОТА
==================================================

Примерный план первых часов:

0:00–0:30
- прочитать кейс;
- выписать требования;
- выбрать 2–3 концепции.

0:30–1:00
- выбрать одну концепцию;
- CASE.md;
- архитектура;
- README skeleton;
- первый подтверждаемый результат / commit.

1:00–2:00
- минимальный end-to-end flow;
- пользователь может пройти главный сценарий.

2:00–3:00
- подключить настоящий AI;
- убрать ключевую mock-логику.

3:00–4:00
- основная бизнес-логика;
- валидация;
- ошибки.

4:00–5:00
- UI;
- demo data;
- удобный demo flow.

Дальше:
- тесты;
- WOW feature;
- deployment;
- README;
- presentation;
- demo rehearsal.

ВАЖНО:
По итогам каждого часа должен оставаться проверяемый результат.

==================================================
10. GIT / РЕПОЗИТОРИИЙ
==================================================

Конкурсная работа — только в официальном репозитории команды.

Делать понятные небольшие commits.

Примеры:

chore: initialize project structure
docs: add case analysis and architecture
feat: implement core input flow
feat: integrate AI extraction
feat: add deterministic analysis
feat: add result dashboard
test: cover core scenario
docs: complete README and deployment guide

Не делать один огромный commit в конце.

Перед каждым важным этапом:
git status

После готового этапа:
git add .
git commit -m "..."

Регулярно:
git push

==================================================
11. DEPLOYMENT
==================================================

Deployment делать заранее, а не перед дедлайном.

Минимум проверить:

- публичный URL открывается;
- backend отвечает;
- frontend загружается;
- AI API работает;
- secrets находятся в environment variables;
- demo data доступны;
- основной сценарий проходит с чистого браузера;
- после перезапуска приложение запускается;
- README содержит URL и инструкции.

==================================================
13. DEMO
==================================================

Demo должно показывать ценность, а не код.

Структура:

1. Проблема — 15–20 секунд.
2. Пользователь — 10 секунд.
3. Решение — 15 секунд.
4. Live demo — главный сценарий.
5. Что именно делает AI.
6. Чем решение лучше очевидного подхода.
7. Как масштабируется.
8. Итоговая ценность.

Не тратить demo на:
- длинный login;
- настройки;
- технические детали;
- показ файлов проекта;
- чтение README.

Если возможно, иметь запасной demo dataset.

"Используем Hackathon Playbook.
Пока никакого кода.
Работаем по этапам:
CASE → VALUE → WOW → MVP → ARCH → SCORE.

Сначала разберем требования кейса и ограничения.
Потом предложи несколько технических концепций.
Для каждой покажи:
- проблему;
- пользователя;
- value proposition;
- главный demo flow;
- роль AI;
- deterministic logic;
- MVP;
- WOW feature;

После обсуждения выберем одну концепцию,
